# Security and Booking Flow Fixes - 2026-09-09

This package fixes five issues identified in the Event Parking Reservation System backend.

## 1. Organizer / Customer IDs in JWT

- Login OTP loading now includes the Organizer and Customer profiles.
- JWTs now include `organizerId` for Organizer accounts and `customerId` for Customer accounts.
- Event controllers can therefore resolve the authenticated organizer correctly.

## 2. Transaction API authorization

Transaction controllers now require JWT authorization and use role checks.

Customer operations no longer trust a customer id supplied in the URL or booking request body. The customer id is taken from the authenticated JWT claim.

Main customer endpoints:

- `GET /api/bookings/me`
- `GET /api/payments/me`
- `GET /api/notifications/me`
- `GET /api/reports/customer/me`
- `POST /api/bookings/{bookingId}/parking`
- `DELETE /api/bookings/{bookingId}/parking`
- `DELETE /api/bookings/{bookingId}`

Admin-only customer-history endpoints are retained where an explicit customer id is appropriate.

Organizer access to event bookings, booking details and booking QR data is restricted to the organizer's own events.

## 3. Payment OTP delivery

Payment OTPs are now sent through the existing SMTP email service to the booking customer's email address.

Configure email credentials using User Secrets or environment variables. Do not commit real credentials to appsettings.json.

The development OTP is hidden by default. It is only returned by the API when BOTH conditions are true:

- Environment is Development
- `Otp:ExposeDevelopmentCode` is explicitly set to `true`

Default setting: `false`.

## 4. Automatic 15-minute pending booking hold

`BookingHold:Minutes` defaults to 15 minutes and `BookingHold:CleanupIntervalSeconds` defaults to 60 seconds.

A hosted background worker now checks for stale unpaid bookings automatically. It runs once when the API starts and then every configured cleanup interval, so expiry no longer depends on a customer making another API request.

When a pending-payment booking becomes stale:

- Booking becomes Cancelled
- Reserved seats are released
- Reserved parking is released
- Pending OTP payment becomes Failed
- Any unused payment OTP record is removed
- Customer receives an in-app booking-expired notification
- Customer receives a booking-expired email when SMTP is configured

The database cancellation and inventory release are saved before email delivery. If SMTP is temporarily unavailable, the booking still expires and inventory is still released; the email error is logged for operators. Existing request-triggered expiry checks remain as an additional safety net.

## 5. Completed payment cancellation / refund safety

A customer can no longer directly cancel a booking with a completed payment.

Admin endpoint added:

`POST /api/payments/{paymentId}/refund`

Because the current payment module is a simulated payment implementation, this endpoint performs an internal system refund/reversal:

- Payment status -> Refunded
- Booking status -> Cancelled
- Seats released
- Parking released
- Booking QR removed/invalidated
- Customer notification created

A real Stripe/PayPal/bank refund API must be connected later when a real payment gateway is integrated.

## Build verification note

The correction environment used to prepare this ZIP does not contain the .NET SDK, so `dotnet build` could not be executed here. JSON and code-structure sanity checks were run. On the development PC, run:

```powershell
cd backend\EventParkingReservationSystem.API
dotnet restore
dotnet build
```

Then test the flows in Swagger using fresh JWTs, because existing tokens do not contain the newly added `organizerId` / `customerId` claims.
